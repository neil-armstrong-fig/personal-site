The brief was a proof of concept: let someone type a sentence, and get back JSON. The client thought that might take me the whole three weeks. In those three weeks I built the entire feature around it: a daily dashboard for the Dashboard Users, AI cost controls, configurable dashboards, and everything in between. I was working on a short-term contract as a Software Engineer for a software company. The feature lets a Manager describe in natural language which key actions their reports should address for the day. It automatically turns this into a daily dashboard for their reports using real system data.

Each dashboard has a short AI-generated summary on top of what is required for the day. This enables them to quickly identify their priorities for the day, and have key deliverables they can measure against.

I worked on the code alone, working with the client's tech lead and product manager for domain expertise. The rest of this piece goes through each week's delivery, and how I used [Claude](https://claude.com/product/claude-code) to get there.

## The problem

Managers need to decide which key actions their reports should address. Dashboard Users need one screen that shows what needs attention. All of this needed to be configurable so Managers could update rules any time they wanted.

_So it's easy then, just let the Manager write the SQL query for each rule themselves, right? No harm in that?_

Obviously this is just asking for trouble. They would need to know your system for a start, and even in a world where they do, it gives them some extremely scary access to the internal data. That was never going to work in practice.

The alternative the client came up with: let the Manager write in natural language what they want from the given "rule", AI translates this into a structured format we can validate in code, and that structured format is then converted (deterministically in code) into SQL that finds the matching records. Everything is validated before it is stored. They don't need to know the system or SQL or tables, just their records and the conditions they care about. The stuff they already know well. They talk to the system in _their_ language, not the system's language. Getting the dashboards and data they need for the Dashboard Users to be extremely productive.

## Week 1: a working flow, end to end

By the end of the first week a Manager could write a rule and a Dashboard User could see the dashboard, connected to the client's systems using synthetic data.

### Talk it through, then show working software

AI can write code faster than I can read it. That is the risk. A lot of wrong code, quickly, costs more than a little right code, slowly. I had Claude writing the code throughout this build, and I was the only developer who knew very little about the domain.

So I never start by asking AI for code and telling it to "_build x, make no mistakes_". I start by talking the feature through with it, going back and forth until the shape is clear and the holes show up. From that I write a `TODO.md`, a running list of small slices of work, and a longer `DELIVERY.md` that says what we're building and why. On top of that, the context I give Claude is a large plan built from the notes I took in the onboarding sessions, flow diagrams of the code since I didn't know it, and what I'd discovered about how the project worked. The TODO is what I think is the original promise of "Agile Development": a living document that expands and changes as we discover hidden gaps in the initial spec. No waterfall here.

The client's tech lead spent half a day walking me through the system, the general terms, and the use case, then handed me an extremely detailed and well thought-out spec. This massively accelerated my ability to deliver quickly. Never rule out how effective just talking to people can be!

One of the most important pieces of information to me as an engineer is the personas: who is using the system and why. Here it came down to a Manager building rules and a Dashboard User consuming them as a dashboard. That ruled out making it too flexible at the start. Flexibility is the end goal, but with two focused personas in mind we could nail down what they wanted while keeping an eye on other use cases for those roles.

For the first two days I had no access to Azure, and the real data the feature needed didn't exist yet in the client's system. That shouldn't stop progress. So I built what I call a "[fuzzy frontend](/blog/fuzzy-frontend/)": a really simple UI that demos every flow with fake data and no API behind it. I generated 500 synthetic samples, ran a [Cosmos DB](https://azure.microsoft.com/en-us/products/cosmos-db/) emulator on my machine, and built the whole flow locally.

By the middle of the first week I had something I could demo to the team to validate their expectations: is this the right flow, is this how you expect each persona to use the system, what about this or that gap? It made for much easier conversation, and it paid off. My own testing had found gaps, so I added a few features before the demo that I thought were required, and the team liked them. We also cut some initially specced features that would have been overkill.

By the end of the first week the fuzzy frontend was no longer "fuzzy". It was working fully through the client's API and databases, with a migration from Cosmos to [Fabric](https://learn.microsoft.com/en-us/fabric/fundamentals/microsoft-fabric-overview) thrown in for good measure. AI let me do that migration in an afternoon, in a background Claude session.

### AI only where it counts

The answer was to give the model one small job and keep it away from everything else.

The AI model that reads the Manager's sentence _never sees any customer data_ and _never writes SQL_. It returns a small piece of structured JSON describing the rule, plus a short title template for each entry on the dashboard. I used the structured output feature in the Azure SDK, which makes the model follow a JSON Schema I supply. [Microsoft's guide](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/structured-outputs) covers it better than I would. It is the model's best attempt, so I don't trust it on its own. Every response goes through a standard JSON validator for required fields and types before any SQL exists. Ordinary C# then turns the validated JSON into SQL in pure code, and the SQL runs read-only. If the model gets it wrong and the check fails, the Manager sees a plain error message. If it gets it right, the same JSON gives the same SQL. Very deterministic results with non-deterministic input.

A second AI step writes the summary. It sees a short summary of the day's dashboard and writes a two or three sentence "summary" for the Dashboard User. Managers and Customer Admins can configure what the summary is asked to write. There are limits on usage and overall budget restrictions in play to prevent runaway costs.

### A small rule language

The rule language is small on purpose. A rule is a list of conditions that must all be true, over a fixed set of supported fields. A smaller language means fewer ways to be wrong, and every rule can be turned back into plain language directly in C#, so a Manager can always read what they have actually asked for.

The Manager gets a plain message that says what the rule can't do and suggests what to try instead. For example, it explains when the requested information is not available. If the AI's answer can't be used, they are asked to rephrase it. If the AI itself is down, they are told that nothing has been saved and asked to try again later. None of these shows technical detail, so a non-technical Manager isn't overwhelmed.

### Proving it

I ran about thirty example prompts through the real system against synthetic records I generated, including prompts that should be refused. For every rule the AI wrote, I recounted the matching records independently from the data generator's own records, and the counts matched. It wrote the rule I intended for nearly all of them, and each refusal gave the reason I expected.

It also showed me where an AI needs a little help from the person using it. A vague description gets a guess at a number, while an explicit threshold gets exactly what was asked. Managers can see the matching records on screen to check a rule before relying on it.

### Let the tests be the fixed point

AI is a non-deterministic tool, so I want something deterministic underneath it. The fuzzy frontend came with a companion deliverable, because [I love ATDD](/blog/acceptance-test-driven-development/): end-to-end tests that run through each journey from the relevant persona's point of view. I wrote them alongside the screens as red and green tests, failing first and then passing. So what I showed was a nice fuzzy frontend, and what I had behind it was a full test suite proving it was correct, ready for the real thing while I built out the API.

By the end there were over 570 tests, all of them end to end. Over 400 run from the frontend, as journey tests written with [Angular's](https://angular.dev/) own testing tools at page or app level, and over 170 run from the backend as integration and API tests. My preference is [Playwright](https://playwright.dev/) and acceptance test driven development, but the client's existing Playwright tests were still early days, and fixing them up would have cost time I didn't have. Page-level journey tests were good enough. It's the same thinking as [Build it again, but better](/software/build-it-again-better/), where I followed a similar approach for software that must be correct, where "it seems to work / maybe works" isn't enough.

## Week 2: keeping the AI affordable

After the first week, I was asked to look at AI cost control, because the client was (understandably) worried about runaway token costs with AI solutions.

This brief was about eight bullet points, so not quite a fully fleshed out spec, meaning - in a somewhat nice way - I had more agency for development.

### One gate for every AI call

My decision was to put both AI calls (rule generation and summary generation) through one gate in the code. This gate records who made the call, which client it was for, what kind of call it was (a Manager writing a rule, or the daily summary for a Dashboard User), tokens in and out, the cost in pounds, how it ended, and a timestamp. It never records the words or the answer. That usage record feeds a screen where System Admins can see what each customer's AI use costs in tokens and pounds, and set limits for them.

### Budgets, and what switches off first

With this in place, the client's System Admins can now set a budget per tenant. When a tenant reaches 80% of it, the less important summary feature switches off first to save budget while keeping the more important rule creation feature active, rules being critical to the dashboard producing good results.

That order was deliberate. Rules are an essential feature, because the dashboard results depend on them. While they likely won't get updated often, when they are it is critical that they are accurate. The summary is a great extra feature that provides huge value, but if budget is running out we naturally want to lose the extra and not the essential first.

### Cheap summaries - my own sprinkling of expertise

A summary that is regenerated for every Dashboard User on every page load would be expensive. While a summary that is just kept all day goes stale the moment a Manager changes a rule or conditions have changed in the system.

So I made a summary refresh only when something that affects it has changed: a new day, a different Dashboard User, a different language, or a change to the live rules. A Manager can switch rules on and off all morning and nothing regenerates automatically. A new summary is only written when a Dashboard User next looks at the dashboard after a change. So it won't cause pointless use of AI and tokens.

## Week 3: one dashboard becomes many

The client's customers have different use cases, and some have several in the one account. So the last part of the build made the dashboards configurable.

### Dashboards and results

I built a management screen where Customer Admins can edit existing dashboards or add brand new dashboards. Each dashboard had a name, a summary, its rules in the order they should appear, its metrics, which roles will see the dashboard, and how many results to show. A preview showed how it would look.

Rule creation now lives in this same place. A Manager's sentence became a rule as before, and the screen previewed the result.

Displayed results for rules could now be fully created and edited here. Their colour, enabled/disabled states, etc.

### Metrics

Metrics are the numbers a dashboard shows for each person over time, such as summary figures by week. They are separate from the rules: rules pick the results, and a metric is its own figure from the same workflow. A Customer Admin describes a metric once in their own words and picks the period (week, month or quarter). They then choose how each dashboard shows it, as a big number, bars or a list of stats, compared with an average or a target. A dashboard can show up to four, and a metric can be switched off. In this build the screens for creating and editing them are a working demo on sample data. The real version, with the AI reading the description and real figures, comes next and waits on a few decisions about what the comparisons mean.

### Roles

Roles decided which Dashboard Users in a customer account could see a dashboard. Creating users and roles already existed elsewhere in the platform, so dashboards used what was there.

## Working with Claude across all three weeks

Two more habits ran through all three weeks.

### Small slices, reviewed, several at once

I used Claude as the driver and kept every slice small enough to review properly, as the human in the loop. Before I clear a session and pick up the next item on the TODO, I review the code and run the app myself. I'm looking at code quality, whether the deliverable is accurate, anything missing or needing an update, and any questions it raises about the domain. I correct course more often than you would think with AI, and the gate keeps the code clean and the direction clear.

Once the fuzzy frontend was in place and validated by the team, I could spin up several Claude sessions, at most four and three on average, each in its own git worktree, to chew through the different areas. The worktrees keep the sessions from clashing, and every change shows up in Visual Studio Code's git tool. They all feed into the same TODO, helping each other with context, and I can quickly jump between the changes to validate the code quality, the output, and the correctness. There is no downtime waiting on Claude when you are running multiple sessions at once. This is where the tests earn their keep, because they tell me quickly if one session has broken what another built. I merged everything into a single branch, and split it up into PRs once I was happy with the end to end.

### Lead the AI

The AI got things wrong often. The first fuzzy frontend that was quickly put together was massively off - using none of the [shared components](/blog/code-system/) or really showing the flows as they should be - so I deleted it and started again. With AI that is easy, because it delivers so fast that throwing code away costs very little. It made assumptions during development that my test-first approach caught when the tests ran. The code it initially wrote didn't follow good standards, so I reviewed it and cleaned up the structure with the sub-foldering approach I use in [Janggi](/software/janggi/), which made a big difference. All of this early on to build as solid a foundation as possible to move extremely quickly. I always find going slow at the start and doing it right with an excellent foundation always pays off.

Plenty of calls along the way were mine, favouring my approach of leading the AI over being led. Keeping the model away from the data and the SQL, and the cheap summaries, are two examples.

## Faster than expectations

In the first week they had a working flow for Managers and Dashboard Users. After three they had the whole system working end to end, built to a much higher standard than a rush job usually gets (this was no "PoC") because the tests and the review gate, the solid foundations, were there from the first day.

My own estimate is that without AI, three weeks would have got me an extremely basic C#-only JSON generator. Certainly as they expected with no UI.

AI completely changes the game for delivery. A quick demo like the fuzzy frontend would normally be a waste of time, or require specialist skills. With AI it was cheap enough to build and rebuild, so the team could react to something real very early and any gaps in the spec could easily be filled and validated.

But like all my delivery, I strive to leave my clients with stuff they can actually use and extend, not just shiny proofs of concept that are deleted and turned off.
